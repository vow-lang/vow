# Plan: issue #1185 — ledger status is entry-wide, so extending an expected entry loses its classification

## 1. Problem restated

`scripts/equivalence.py::propose_ledger` merges a newly-found (untracked) divergence into an
existing corpus entry by unioning `observable` and then unconditionally setting
`entry["status"] = "open"` (lines ~909-929). When the entry was previously `status: "expected"`
(a reviewed, documented asymmetry backed by `note`/`issue`/`*_error_codes`), extending it with an
unrelated new observable silently discards that classification: the proposal shows the whole
combined entry as `open`, with no record that one of its observables was already reviewed. The
schema (`docs/equivalence/ledger.schema.json`) only has one `status` per entry even though
`observable` is already plural, so there is nowhere to put the finer-grained fact. Functionally
nothing breaks today (`reconcile()` suppresses `open` and `expected` identically, and `note`/
`issue`/error-code multisets already survive the merge untouched), but the proposal loses
information a human reviewer needs, and that is the bug: the ledger should represent both
classifications, not erase one of them.

## 2. Files to touch

This is a tooling/data-model change confined to the Python equivalence harness — it does not touch
`crates/` or `compiler/` (no Vow language surface, no codegen, no verification pipeline).

- `docs/equivalence/ledger.schema.json` — add an optional, additive `expected_observables` property
  to the `corpus` entry schema (see §3 below for exact shape). No `schema_version` bump: the field
  is optional and every existing document (all 17 current entries, none multi-observable) remains
  valid and unchanged in meaning without it, unlike the fuller `observables: {name: {status,...}}`
  restructure the issue sketches as its first option — that one *would* need a version bump and is
  explicitly out of scope here (see §6).
- `scripts/equivalence.py` — `propose_ledger()`'s new-findings loop (currently ~line 909-929) and
  its fixed-findings loop (currently ~line 894-907) gain the `expected_observables` bookkeeping
  described in §3. `reconcile()`, `divergence_matches_entry()`, and `tracked_observables()` are
  **not** touched — suppression already keys only on entry-wide `status in ("open", "expected")`,
  and that check is unaffected by this field (confirmed by reading both functions; see §5).
- `scripts/test_equivalence.py` — new tests in `ProposeLedgerTest`, plus updates to the shared
  `assert_valid_ledger_document` helper (~line 63-99) so it knows the new field's invariants.
- `docs/equivalence/ledger.json` — no data migration needed (no current entry is multi-observable),
  but leave it untouched by hand; it is regenerated by tier-3 review, not by this PR.
- `docs/equivalence/README.md` — extend the "Tier-1 parity suppressions" section (~line 201-212)
  with 2-3 sentences documenting `expected_observables`: what it means, and that it is a proposal
  aid, not a suppression-semantics change.

No `docs/spec/*.md` update: this is CI/tooling metadata, not Vow language syntax, semantics,
builtins, or CLI surface.

## 3. TDD slices

Work from `scripts/test_equivalence.py`'s existing `ProposeLedgerTest` class, which already covers
adjacent cases (`test_new_observable_extends_an_existing_entry`,
`test_an_open_error_code_entry_keeps_its_multisets_when_a_gap_is_added`). No test currently exercises
extending an `expected` entry — that gap is exactly why the bug shipped unnoticed.

1. **Red: extending an `expected` entry with a new observable must not lose the classification.**
   Add `test_extending_an_expected_entry_preserves_its_classification` to `ProposeLedgerTest`:
   original entry `{"observable": "error_code", "status": "expected", "note": "...", "issue": 588,
   "rust_error_codes": [...], "self_hosted_error_codes": [...]}`, `new = [{"file": "a.vow",
   "divergences": [{"observable": "runtime"}]}]`. Assert the proposed entry has
   `observable == ["error_code", "runtime"]`, `status == "open"` (fail-safe direction is
   preserved — a reviewer must still look at the new `runtime` finding), `expected_observables ==
   ["error_code"]`, and that `note`/`issue`/`rust_error_codes`/`self_hosted_error_codes` are
   unchanged. Also assert via `assert_valid_ledger_document`. This fails today because the entry
   currently has no `expected_observables` key at all.

2. **Green: implement the classification carry-over in `propose_ledger`'s new-findings loop.**
   In the `for record in new:` loop, before overwriting `entry["observable"]`/`entry["status"]`,
   compute:
   - `was_fixed = entry.get("status") == "fixed"` (already computed as the basis for `carried`).
   - `prior_expected = carried if entry.get("status") == "expected" else frozenset(entry.get("expected_observables", [])) & carried`.
     Write it as this single expression, not a three-way if/elif — the `& carried` is not
     defensive filler, it is what makes the `was_fixed` case fall out correctly for free (`carried`
     is already `frozenset()` for a reopened `fixed` entry, so intersecting collapses
     `prior_expected` to `frozenset()` too, mirroring the existing reset for stale error-code
     multisets) and it enforces the subset-of-`carried` invariant without a separate guard.
   - After computing `entry["observable"]` as today, set `entry["status"] = "open"` as today, then:
     `entry["expected_observables"] = sorted(prior_expected)` if `prior_expected` else
     `entry.pop("expected_observables", None)`.
   Every record reaching this loop carries only *untracked* divergences (reconcile's `as_new`), so
   `prior_expected` (⊆ previously-tracked `observable`) and the newly-found observables are always
   disjoint — no need to guard against `prior_expected` swallowing the whole new set.

3. **Pin: an already-`open` entry that already carries `expected_observables` must keep it
   unaffected by an unrelated further extension.** Add
   `test_further_extending_a_mixed_entry_keeps_its_prior_expected_observables`: original entry
   `{"observable": ["error_code", "runtime"], "status": "open", "expected_observables":
   ["error_code"], "note": ..., "issue": ...}`, extend with a new `exit_code` divergence. Assert
   `observable == ["error_code", "exit_code", "runtime"]`, `expected_observables` still
   `["error_code"]`. This passes as soon as step 2 lands (write it alongside step 2, not as a
   separate red step — there is no production code left to drive after step 2's single expression
   is in place); it exists to pin the behavior against future regressions, not to prove step 2.

4. **Pin: reopening a `fixed` entry must not resurrect a stale `expected_observables`.** Add
   `test_reopening_a_fixed_entry_drops_its_stale_expected_observables`, mirroring the existing
   `test_reopening_a_fixed_entry_drops_its_stale_error_code_multisets`: original entry has
   `status: "fixed"` and a leftover `expected_observables` from before it was fixed; extend with an
   unrelated new observable; assert the proposed entry has no `expected_observables` key. Also
   passes immediately once step 2's `& carried` lands; written alongside step 2 to pin it.

5. **Red: a partial fix must drop the fixed observable from `expected_observables`, not just from
   `observable`.** Add `test_partial_fix_prunes_the_fixed_observable_from_expected_observables`:
   original entry `{"observable": ["error_code", "runtime"], "status": "open",
   "expected_observables": ["error_code"], ...}`, `fixed = [{"file": "a.vow", "observables":
   ["error_code"]}]` (the *expected* half stopped reproducing, the *open* `runtime` half is
   untouched). Assert the proposed entry has `observable == "runtime"` and no
   `expected_observables` key (it would otherwise reference an observable no longer in
   `observable`, breaking the subset invariant). This fails today because the fixed-findings loop
   never touches `expected_observables`.

6. **Green: prune `expected_observables` in the fixed-findings loop.** In the `for finding in
   fixed:` loop (~line 894-907), after computing `remaining`, also compute
   `remaining_expected = frozenset(entry.get("expected_observables", [])) & remaining` and either
   set `entry["expected_observables"] = sorted(remaining_expected)` (if non-empty) or
   `entry.pop("expected_observables", None)`. Add this inside the `if remaining:` branch only —
   the `else` branch (full fix → `status = "fixed"`) already retains the entry's fields verbatim by
   design (per `test_fully_fixed_entry_keeps_its_history`), and `expected_observables` should be
   retained there too as part of that same history, so it needs no new code.

7. **Schema: add the `expected_observables` property.** Update
   `docs/equivalence/ledger.schema.json`'s corpus-entry schema:
   ```json
   "expected_observables": {
     "type": "array",
     "items": { "$ref": "#/$defs/observableName" },
     "minItems": 1,
     "uniqueItems": true,
     "description": "The subset of 'observable' that was reviewed and classified 'expected' before a different observable's divergence forced the entry-wide 'status' to 'open'. Every name here must also appear in 'observable' (enforced by propose_ledger's construction and by the test suite, not by this schema — 2020-12 has no cross-property subset keyword). Purely a review aid: reconcile() suppresses by the entry-wide 'status' alone, so this does not change suppression behavior."
   }
   ```
   and an `allOf` clause requiring `status == "open"` plus `note`/`issue` whenever
   `expected_observables` is present (mirrors the existing `expected`-status `note`/`issue`
   requirement — the rationale for classifying part of a mixed entry as expected needs the same
   justification as classifying the whole entry that way):
   ```json
   {
     "if": { "required": ["expected_observables"] },
     "then": {
       "properties": { "status": { "const": "open" } },
       "required": ["status", "note", "issue"]
     }
   }
   ```
   Add `"expected_observables"` to the entry's `properties` map (required for
   `additionalProperties: false` to keep accepting it).

8. **Test the schema addition against the stdlib-only mirror.** Update
   `assert_valid_ledger_document` (scripts/test_equivalence.py:63-99): extend `allowed_keys`
   coverage (already derived from the schema's `properties`, so no change needed there — verify
   this by running the suite, don't hand-edit the derivation), and add the two invariants the JSON
   Schema itself cannot express:
   - `expected_observables ⊆ declared` (the subset-of-`observable` invariant).
   - when `expected_observables` is present and non-empty: `status == "open"` and `note`/`issue`
     are present (same shape as the existing `expected`-status check just above it).
   Run this helper against all six new/updated tests from steps 1-6 to confirm the schema and the
   Python-level invariant agree.

9. **Regression check: run the full existing suite.** CI runs this file as a bare script
   (`.github/workflows/ci.yml:77`: `python3 scripts/test_equivalence.py`, from the repo root, plain
   `unittest` — no `pytest`, no `bench/` project involved). Run it the same way locally:
   `python3 scripts/test_equivalence.py -v`. Confirm no existing `ProposeLedgerTest` case
   regresses, particularly `test_an_open_error_code_entry_keeps_its_multisets_when_a_gap_is_added`
   (status already `open`, no prior `expected_observables` — must produce no `expected_observables`
   key at all, not an empty list) and `test_untouched_data_round_trips_and_corpus_keys_are_sorted`
   (entries never touched by `new`/`fixed` must be byte-identical, including absence of the new
   key).

10. **Documentation slice (no production code).** Add the 2-3 sentence note to
    `docs/equivalence/README.md`'s Tier-1 section (§2 above). This is documentation only and can
    land in the same commit as step 7, or its own trivial commit — either way it is not a
    behavior-driving TDD step, so it is listed last.

## 4. Verification surface

Not applicable in the ESBMC/contracts/codegen sense — this change touches only the Python
equivalence-sweep tooling (`scripts/equivalence.py`, its schema, its test file, and a doc). There
is no Vow source, no IR, no C model, and no `tests/run/`/`examples/` fixture to grow. The
"verification" here is the JSON-Schema-plus-`assert_valid_ledger_document` pairing described in
slices 7-8, and the existing `scripts/test_equivalence.py` suite plus the equivalence CI workflow
(`.github/workflows/equivalence.yml`), which only checks for `ledger.proposed.json`'s existence and
prints new-divergence summaries — confirmed by reading the workflow file, it does not need changes.

## 5. Risk areas

- **None of the binary-fixed-point concerns apply.** This PR does not touch `compiler/` codegen
  ordering, `vow-clif-shim` stack-slot layout, or `BTreeMap`/`HashMap` choices — it is pure Python
  tooling outside the compiler pipeline entirely.
- **`parse → print → parse` idempotency is not implicated** — no Vow syntax or printer change.
- **`cargo clippy --all -- -D warnings` is unaffected** — no Rust source changes. The relevant gate
  for this PR is the Python test suite and whatever lint gate covers `scripts/*.py` (per project
  memory: CI pins a specific `ruff` version — verify with `uvx ruff@<pinned-version>` rather than a
  locally-installed newer `ruff`, to avoid chasing lint findings CI will never actually enforce;
  find the exact pin from CI config before running).
- **Schema/helper drift.** `assert_valid_ledger_document` is a deliberate hand-maintained subset of
  the JSON Schema (its own docstring says so) for tests that avoid a `jsonschema` dependency. The
  real risk here is forgetting to update it when the schema gains the new property/constraint —
  slice 8 exists specifically to keep them in sync, and the existing `allowed_keys` line already
  derives from the schema so no double-maintenance is introduced there.
- **Subset invariant is not machine-checked by the schema.** `expected_observables ⊆ observable` is
  enforced only by (a) `propose_ledger`'s construction and (b) the Python test helper, not by JSON
  Schema validation itself (2020-12 has no built-in cross-property subset keyword short of `$data`,
  which is not part of the spec). If a human hand-edits `ledger.json` and violates this, schema
  validation will not catch it. This is a known, accepted limitation — flag it in the schema
  property's `description` (done in slice 7) rather than attempting a schema-level workaround that
  would add fragility for a hand-edit case with low actual likelihood (entries are almost always
  written by `propose_ledger`, then hand-reviewed for `note`/`issue`, not hand-constructed from
  scratch).
- **Scope discipline.** It is tempting to also make `propose_ledger` auto-collapse a mixed entry
  back to a clean entry-wide `status: "expected"` once the non-expected observable(s) get fixed and
  only the previously-expected ones remain. Deliberately not doing this (see §6) — it's a
  usability nicety, not required to close the issue, and adds another branch to reason about and
  test.

## 6. Out of scope

- **The fuller `observables: {name: {status, note, issue, ...}}` restructure** the issue floats as
  its first option. That is a genuine breaking schema migration (would require a `schema_version`
  bump, touching every consumer of the current flat `observable`/`status`/`note`/`issue` shape,
  including `reconcile()`, `divergence_matches_entry()`, and every hand-written `ledger.json`
  entry). The additive `expected_observables` list closes the issue with far less churn and no
  version bump; the richer restructure is left as a future option if per-observable `note`/`issue`
  (as opposed to just a classification flag) is ever actually needed.
- **Auto-collapsing a mixed entry back to `status: "expected"`** once its non-expected half is
  fixed (see risk-areas note above) — not required by the issue, adds branching, left alone.
- **Changing `reconcile()`/`divergence_matches_entry()`/`tracked_observables()`.** Confirmed by
  reading both functions that suppression already treats `open` and `expected` identically and
  never reads `expected_observables`; adding logic there would be scope creep beyond what the
  issue asks for (a proposal-writer fix), matching the original PR #1177 deferral rationale almost
  exactly.
- **Migrating `docs/equivalence/ledger.json` by hand.** No current entry needs it (none are
  multi-observable today); leave the live ledger data untouched in this PR.
- **Any Rust or self-hosted compiler change, and any `docs/spec/*.md` update.** This issue has no
  language-surface component.
- **General refactoring of `scripts/equivalence.py`** beyond the two loops in `propose_ledger`
  named in slices 2 and 6 — e.g., do not restructure `reconcile()`'s return shape or rename
  unrelated helpers while in the file.
