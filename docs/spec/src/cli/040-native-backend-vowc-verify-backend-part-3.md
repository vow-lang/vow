- **Collections.** A `Vec<T>` with `T` of `bool`, an integer (`i128` and `u128` included) or a float (`new`, `push`, `v[i]`, `v[i] = x`, `len`, `pop`, `clear`, `truncate`, `vec_sort`, `Vec::from_raw_parts_copy` and `pin_to_root`) is an array plus a 64-bit symbolic length; a 128-bit element is two 64-bit slots of that array, read and written together, so its length, bounds obligation and counterexample contents are those of any other `Vec` (a listed element is one 128-bit value); a float element is the same 64-bit slot the runtime keeps (an `f32` in its low 32 bits), read through `to_fp` and written as the bits of a float constant or, for any other float, a fresh bit pattern assumed to be one of that float, so a float written and read back is equal to itself (every NaN is the one SMT NaN, so a NaN's payload does not survive, and a property that needs `x == x` states it) and a listed element is the float as a decimal; `Vec::from_raw_parts_copy(p, n)` is empty for a null `p` or `n == 0` and otherwise `n` elements of unknown contents (a length at the runtime's limit traps, so it never returns), and `pin_to_root` is a copy: the same length and elements in a separate object. There is no capacity: a parameter's length is unconstrained apart from the runtime's own limit (a Vec's length is below `2^63 - 1`, so `v.len() as i64 >= 0`), and a `push` is assumed to return only while the length stays below it, so a property over every length is proven for every length, not only up to ESBMC's model capacity. An index at or past the length is an obligation of its own on `get` and `set`: a counterexample is `VerifyFailed` with the unattributed vow id `4294967293`, blame `None` and violation text `index out of bounds`. A `Vec` parameter's length is listed in `values` as `<param>.len` and its elements below that length as `<param>[0]`, `<param>[1]`, ... (see "Counterexample contents of `Vec` and `String` parameters" below); two `Vec` or `String` parameters of one declared type may be one object, as a caller can pass one value for both: a function that changes one of them gives each an identity (listed as `<param>.alias`), two are one object exactly when their identities are equal, and a write through one is a write through the other then (#1823). Every `ensures`, `invariant` and abort check holds for every identity assignment, so a contract that is true only when the two are different (`ensures: dst.len() == old_len + src.len()` of an `append(dst, src)`) is `VerifyFailed` with equal identities, and the contract has to hold either way; the declared type decides the group, so `Vec<Id>` and `Vec<i64>` are one type under `type Id = i64`. A `String`, `Vec` or struct pushed or stored (`Vec<Vec<_>>`, `Vec<String>`, `Vec<struct>`) takes the 8-byte slot of its address. A function that never looks at the slot again keeps it as a fresh constant: the length, the bounds of every index and the other elements are exact, and the `Vec` can be returned or passed on. A function that reads an element back holds the address of the object instead (the address a pointer stored in a struct field has, see "Memory read through a field"): `outer[i]` is the `String`, `Vec` or struct stored at `i`, and a read through it (`len`, `get`, `byte_at`, a field) is a read of that object at that point of the function, so a push made after the store, an overwritten slot, one object in two slots and `pop`, `clear` and `truncate` behave as they do at run time. That needs every `Vec` a pointer is stored into to be one the function created empty with `Vec::new` (the elements of a parameter are memory the caller gave, which the model cannot tell from the stored object), every pointer stored to be a struct parameter, an allocation, a literal or a `String` or `Vec` the function built (a handle read out of another `Vec` is not an address the model knows, and two `Vec` or `String` parameters may be one value, #1823, so such a parameter stays `Skipped`), and no element read of any other `Vec` to be used as an object. **`Skipped`** is a function outside that which could look at the slot, as `unsupported-opcode`: it reads such an element back with `get` (`a pointer element is read back`, which includes using an element of an element as an object, `outer[i][j].len()`; a scalar `outer[i][j]` is modelled), copies or sorts a `Vec` that holds one (`a Vec of pointer elements is copied`), or reads memory through a handle (`a pointer element is stored in a function that reads memory through a handle`), because the stored object may be what a loaded handle names. A function that reads memory through a handle and never reads an element back is still modelled when every `Vec` a pointer is stored into is one the function built and no pointer an element read through memory returned is used as an object. A `Bool` or integer field written through an element (`people[i].age = v`) is a write to the object the slot holds, the one `i` selects, so the variable it was pushed from, another slot holding it and a later read through an element all see it; it needs the same `Vec::new`-built `Vec`; a struct parameter stored into it is the caller's object, so the write reaches every parameter of that type that may be the same object (the `alias` identities of a counterexample), and a function with such a write is decided by unwinding alone (its loops are never cut). A field written through the element of any other `Vec`, a pointer or float so written, and an element of an element (`grid[i][j].age = v`) stay **`Skipped`**. The remaining cases are tracked by #1663. **`Skipped`** also: `reserve`, a 128-bit element read through a struct field, an index that is not 64-bit. Two Vecs merged by an `if`/`else` (or returned on two paths by a callee) are one value that stands for the one picked: a read sees that Vec, and a write reaches exactly that Vec under the condition that picks it, so every other name for either sees it (`let v = if c { a } else { b }; v.push(1)` pushes onto `a` when `c` holds and onto `b` otherwise). A loop that switches the Vec a variable names is not cut by its `invariant`: a symbolic bound there is decided by unwinding alone, `unknown` when the unwinding assertion cannot be discharged. Reading an element of a `Vec<struct>`, `Vec<Vec<_>>` or `Vec<String>` is modelled as memory (see "Memory read through a field"). `vec_sort(v)` is a new `Vec` of `v`'s length that is the sorted permutation of `v` (ascending, signed): every slot is at or below its successor and the slots are exactly `v`'s in another order, stated with quantifiers for every length, so the result is determined; sorting leaves `v` unchanged and a later write to `v` does not move the result. A Vec passed to another function is inlined (see "Calls"). **Maps.** A `HashMap<K, V>` or `BTreeMap<K, V>` whose key is `bool` or an integer of at most 64 bits and whose value is `bool`, such an integer or `()` (`new`, `insert`, `get`, `contains_key`/`contains`, `remove` on a `HashMap`, `len`) is three terms: a presence array from 64-bit keys to 0 or 1, a value array and a 64-bit symbolic length, with no capacity (the only length fact is the runtime's, that a table of that many entries is addressable, so a length is below `2^63 - 1`). A key or value is the 8-byte slot the runtime stores, so two keys are equal exactly when their slots are, and `get` and a `BTreeMap`'s `insert` return an `Option` that is `None` with payload 0 for an absent key. A `BTreeMap` is modelled like a `HashMap`: the runtime has no iteration API, so neither its key order nor the slot a `HashMap` key hashes to is observable. A map built in the function (`new`, then `insert` and `remove`) is exact. A map parameter, or the state a loop cut forgets, is an arbitrary key set and length, with the one fact a real map has that can be stated without a quantifier: the number of distinct keys the function names that are present is at most the length. With 64-bit keys that is all a real map needs, so a counterexample is a run. A key narrower than 64 bits (`bool`, or an integer of 8, 16 or 32 bits) bounds the length of a map by its domain, a `HashMap<u8, V>` holding at most 256 entries; the declared key type of a map parameter is known, so the model adds for every key the function names that a key outside the domain is absent and that the length and the number of distinct named keys that are in the domain and absent fit in the domain together. A counterexample is then a run too, and a `requires` no such map can meet (`m.len() == 300` for `u8`) is unsatisfiable. A counterexample lists a map parameter's length as `<param>.len` and each key the function asks it about as `<param>[<key>]` (see "Counterexample contents of `Vec` and `String` parameters" below). A map the function built whose state a loop cut forgets, a key type the compiler did not record, and narrow-key map parameters that may be one object (below) may have a length above the key domain that the model does not know, so a counterexample that depends on the keys or length of such a map is `verify_status: "unknown"` with a message that starts `unconstrained map state:`, unless the failure holds for every state. Map parameters of one declared type (`HashMap<i64,i64>` and `BTreeMap<i64,i64>` are two types) may be one object, as `Vec` and `String` parameters may: when the function changes one of two such parameters, each gets an identity listed as `<param>.alias`, two are one object exactly when their identities are equal (their initial contents are then equal), and an `insert` or `remove` through one is applied to the other under that test; what one of them shows of the key width holds for the others (#1858). **`Skipped`** as `unsupported-opcode` (detail names the cause): a key or value that is not `bool`, an integer up to 64 bits or `()` (a `String`, `Vec`, struct or map value, or a 128-bit integer), a map passed to another function, stored in a struct field, or merged by an `if`/`else` that yields different maps. A loop that writes a map is decided by unwinding and invariant induction alone, and the map's contents are unconstrained at the top of the loop in the inductive attempt.
