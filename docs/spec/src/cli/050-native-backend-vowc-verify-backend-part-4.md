- **Memory read through a field.** A struct, `Vec` or `String` that is a field of a struct, and an element of a `Vec`, is reached through a pointer the function loaded. The IR types such a pointer `i64`, so the verifier treats it as a 64-bit address, never as an object: a field `k` of the object at `h` is `hf<k>[h]`, the length of the collection at `h` is `hlen[h]` and its element `i` is `helem[h ++ i]` (a 128-bit key), each an unconstrained SMT array that is never written. Two reads of the same field are one address, so `b.insts.len()` and `b.insts[n - 1]` agree on which `Vec` `b.insts` is, and the model puts no cap on a length, a field or an element (a length is below `2^63 - 1`, the runtime's own limit, like every `Vec`). A `Bool` or integer field of up to 64 bits, a `Vec` or `String` length, a `Vec` element (a 128-bit one is the two slots `2i` and `2i + 1`) and a `String` byte can be read this way, to any depth (`ctx.func.blocks[i].insts[n - 1].op`); an index at or past the length is the same obligation as for any `Vec`. The arrays are never written, and a parameter may be the very object an address names (`q.child` is `p`), so a function that reads memory this way and also writes a parameter (`FieldSet` on a struct parameter, `push`, `set`, `pop` or a `String` mutation on a `Vec` or `String` parameter) lays the state of its parameters over them: each `Vec` or `String` parameter and each struct parameter the function uses carries a free 64-bit address, and a read through the address `h` is that parameter's own current state (the length, element, byte or field the writes before the read made it) when `h` is its address, and the array's otherwise. That is exact and has no quantifier, and a loop's cut havocs the parameter the loop writes as it does without reads through memory. A `Vec` or `String` is never a struct, so a length, element or byte read can name only a `Vec` or `String` parameter and a field read only a struct parameter, and a `String` operation names only a `String` parameter, a `Vec` operation only a `Vec` parameter; two `Vec` or `String` parameters of one type, like two struct parameters, are one object exactly when their identities say so (see "Aggregates" and "Collections"). A read through a struct-typed field's address also assumes the field edges it was produced by are ranked: the value a by-value struct-typed field holds ranks below the object holding it. No program can hold a struct whose by-value struct field resolves back to an object the same path already crosses (a literal is a tree, the language has no null, no placeholder and no uninitialised `let`, and `p.next = p` needs a `p` whose `next` exists), so a cycle through by-value struct-typed fields is no state a program reaches and the model does not report one: a cycle's edges would force the rank to decrease around it, while an acyclic state keeps any topological ranking of its addresses. A handle may stand for any parameter of its class even where the source types differ. A counterexample lists each address as `<param>.addr`, so a field whose value is an address shows which parameter it aliases. A function declared to return a `String`, `Vec` or struct may return such an address (a getter, `fn name(p: Person) -> String { p.name }`, or `v[0]` of a `Vec<String>`): the call's result is the handle, read through the memory model like any other, and a Phi that merges only handles is one. A merge of a handle with an object the function built (`if c { v[0] } else { String::from("x") }`) has no model and is **`Skipped`** as `unsupported-opcode` (`Upsilon type differs from its Phi`). Building and mutating a fresh value is unaffected: no handle can name it. Writing through an address (`push`, a `String` operation other than `len` and a byte read, a field write other than the one through an element of a `Vec` of pointers that "Collections" describes) and reading a float or 128-bit field through one are **`Skipped`** too. A pointer written into a field of a struct (`S { ids: a, names: b }`, `h.items = v`, `o.inner = i`) stores the object's 64-bit address in the slot, and a read of the field returns that address, so the collection or struct read through it is the object itself at that point of the function: a `push` after the store is what the read sees, and two fields hold two objects. An object the function allocated gets a free address of its own when it is first stored, distinct from the address of every other object, and a parameter that is stored has the address a parameter has for the aliasing rule above. A pointer chosen by a branch stores the address of the object each edge supplies, so a read sees the object of the path taken, and a store in a branch keeps the old address on the paths that skip it. A value read out of the memory the function was given (a parameter's field, a field or an element read through a handle) is assumed to be none of the objects the function allocates, since an allocation is no object that existed before it; only an address the function stored can be the handle a read then names. A store into a parameter's field is a field  write like any other and follows the aliasing rule of "Aggregates". A write through a collection held in a field (`b.insts.push(x)`, `b.insts[i] = x`, a `String` operation that changes the string) is a write to the object the field holds when exactly one store of the field may name the struct (a struct the function or a callee built, stored once with a pointer whose store dominates the read): `b.insts` is then that stored object wherever an object is needed, and a loop that writes `b.insts` is a loop that writes that `Vec`. A second store of the field, a store after the read, a store through a pointer the function loaded when the struct was itself stored into a field, pushed into a collection or passed as a value, and a field of a parameter are not resolved, and a write through such a handle is **`Skipped`**. A counterexample lists the fields of a parameter read through memory like any other, so a `Vec` or `String` field of `b` is `b.<slot>` with the address as its value; when the function measures the collection (`len`, `v[i]`, `byte_at`), its length is `b.<slot>.len` and its elements are `b.<slot>[<i>]`, listed like those of a `Vec` or `String` parameter (see "Counterexample contents of `Vec` and `String` parameters"). A collection reached any other way (a field of a struct the function loaded from a field, an element of a `Vec`, a merge of two fields) is not listed. `--replay-cex` rebuilds a listed `Vec` or `String` field, binds a field whose value is the address of a parameter to that parameter, and reports `"skipped"` for a collection it cannot (see "Native backend" under "Counterexample replay").
- **Strings.** A `String` is the same array plus 64-bit symbolic length as a `Vec`, with no capacity and the runtime's own length limit (below `2^63 - 1`); byte `i` is the low 8 bits of its slot, so every read is in `0..=255`. Modelled: `String::new`, a literal, `String::from` and `pin_to_root` (each a copy), `String::from_raw_parts_copy` (empty for a null source or a zero length, else that many bytes of unknown contents; a length at the runtime's limit traps and so never returns), `len`, `push_byte`, `push_str`, `clear`, `byte_at`, `eq`, `substring`, `string_substr`, `string_starts_with`, `string_ends_with`, `contains` and `string_matches_literal_at`, with the clamping and the no-wrap `pos + len` rule of [`grammar.md`](grammar.md#string-offsets). `byte_at` at or past the length is an obligation of its own, `VerifyFailed` with the unattributed vow id `4294967293`, blame `None` and violation text `index out of bounds` (the verifier is stricter than the runtime, which returns `-1`). `eq` is exact, for strings of any length: equal lengths and every byte equal, never a length shortcut, a hash or an uninterpreted function. It is a finite conjunction when both lengths are small constants and otherwise a quantified assumption (the query then uses the `ABV` logic instead of `QF_ABV`; the quantifier is never in the negated goal). `contains` is exact too: true for an empty needle and when some start up to `len - needle.len` matches, false otherwise, stated by a witness start for the true direction and a Skolem position per start (a binder in an assumption, plus its first and last instance) for the false one, so a property that needs the false direction of two related searches (`a.contains(b) && b.contains(c)` implies `a.contains(c)`) is a quantified query the solver may not close, and is then `verify_status: "timeout"` or `"unknown"`, never a proof. A function that reads no byte of any string is given no byte facts at all. A `String` parameter's length and bytes are listed in `values` as `<param>.len` and `<param>[<i>]` (see "Counterexample contents of `Vec` and `String` parameters" below); two `String` parameters may be one object, as for `Vec`. The equality is exact, and two differently built equal strings (`(a + b) + c` against `a + (b + c)`) are decided: the byte at a differing index is read through the appends that built it, so the solver splits on the lengths instead of instantiating the quantified definitions. That unfolding is bounded in size and falls back to the array beyond it, which keeps the query exact but may make it slow, and then `verify_status` is `"timeout"` or `"unknown"`, never a proof. `hash_str` is exact: the runtime's FNV-1a fold over every byte (offset basis `0xCBF29CE484222325`, prime `0x100000001B3`, wrapping), a closed term when the length is a small constant (so the hash of a literal folds to the runtime's value) and otherwise the entry `len` of a fresh prefix array that a binder in an assumption defines (`h[0]` is the basis and `h[i + 1] == (h[i] xor s[i]) * prime` below `len`). `hex_encode` is exact: `2 * v.len()` bytes, the digits `0123456789abcdef` of the high and the low nibble of each element's low 8 bits. `hex_decode` is exact, including the runtime's strictness: empty unless the length is even and every pair is a hex digit, optionally after a `+` (`u8::from_str_radix` accepts a leading plus sign), else `len / 2` bytes. Their binders stand only in assumptions, so a proof or a counterexample that has to reason through one may end `verify_status: "timeout"` or `"unknown"`, never a wrong verdict. `parse_<int>` (`parse_i8` to `parse_u128`, and the `u64` method), `string_trim`, `string_to_upper` and `string_to_lower` follow Rust's Unicode-aware `str` methods (a non-ASCII character can change the length, invalid UTF-8 gives the empty string or `None`), which the model does not encode, so each is an opaque total function of the bytes of its string, like `parse_f64_bits`: a fresh constant (the Some flag and a payload of the parsed width, or an array and a length for a text), equal strings give equal results, and the facts every run has are kept (a payload fits its type, `string_trim` never grows a string, a case map keeps the empty string empty). `replace(s, from, to)` is the same kind of function of its three strings: a fresh text whose length is below the runtime's limit, shared by calls on the same operand terms and equal for equal operand strings. `split(s, sep)` is a `Vec<String>` of a fresh array and length with the facts every run has (at least one piece, at most `s.len() + 1`, exactly one for an empty `sep`, and the same count for equal operand strings); its elements are addresses of strings the model does not hold, so an element read through is a read of unconstrained memory and a counterexample that needs one is `unknown`. `join(parts, sep)` is a fresh text whose length is below the runtime's limit and is empty for no parts; it states no congruence, because the runtime reads the contents of every part, which the model does not hold for an object the function stored. A claim that holds for every result is proven; a counterexample that depends on a result is `unknown` (`opaque builtin result`), never a counterexample. **`Skipped`**: `String::from_cstr` and the arena variants (`unmodeled-builtin`; the reason is in `compiler/vc_strops.vow`), a `String` stored in a struct field and passed to another function (merged by an `if`/`else` that yields different strings is modelled like a `Vec`), and a string literal that is mutated (the runtime traps on it). None of the skips is a cap: each is a semantics the model does not encode exactly or a result it cannot hold. `from_cstr` reads memory behind a C string, and an arena variant takes an extra region operand that has no model; a byte-wise approximation or an unconstrained result would let a counterexample be spurious, so the caller is skipped instead.
