- **Aggregates.** A struct, enum, `Option` or `Result` value is scalarised: each field is its own `bool`, integer or float term (a 128-bit field is one 128-bit term; a float field is a term of its float sort, and a slot written at one sort and read at another reads as unconstrained, so no bit pattern is reinterpreted), so construction, field access and `match` need no heap model. A parameter's fields are unconstrained, and so is its discriminant: no range is assumed for an enum tag. A field a construction did not write (the payload of `None`) is unconstrained too, never `0`. Two aggregates merged by an `if`/`else` or a `match` are merged field by field. A field write is path-conditional: a write in a branch keeps the old value on the paths that skip it, so a struct literal whose field value contains an `if`, a `match` or an `.unwrap()`, a field of a value built before a branch, and a field of the only struct or enum parameter are all modelled. A counterexample lists the fields of a struct, enum, `Option` or `Result` parameter in `values` under `<param>.<slot>` (the IR carries no field names): a struct's fields are `p.0`, `p.1`, ... in declaration order; an enum's discriminant is `p.0` (variant index in declaration order; `Option` is `None` = 0, `Some` = 1; `Result` is `Ok` = 0, `Err` = 1) and the chosen variant's payload starts at `p.1`; a 128-bit field takes two slots and so shifts the slots after it by one. Only slots the function reads are listed, and a claim lists those read before it in the walk (a slot read only after the claim, or never, is absent). A slot the function reads at two different sorts (an `i64` payload in one variant, a `bool` or an `f64` in another) gets a `:bool`, `:f32`, `:f64` or `:<bits>` suffix on every one of its names (`o.1:64`, `o.1:bool`). `bool` fields print as `true` or `false`. A field write through a merged value (`let p = if c { a } else { b }; p.f = 1`) is a write to each value the merge may stand for, under the condition that selects it. Parameters may be one object (the caller can pass one value twice): when a function writes a field through a parameter and reads or writes fields of, or merges, at least two struct, enum, `Option` or `Result` parameters, every such parameter carries a free identity and two parameters are the same object exactly when their identities are equal. A write to one is then also a write to every other under that test, and their unwritten fields are equal when they alias. Two parameters may alias only when their declared types have the same head (`Cell` and `Cell`, `Option<A>` and `Option<B>`): the lowering records each parameter's type head with type aliases resolved, and parameters of different heads, such as two structs of different types, are never one object; a parameter alone in its head has no identity, and when a head is not known all of them are one group, as under ESBMC. A counterexample lists each identity as `<param>.alias` (equal values mean one object), a parameter that is the same object as an earlier one shows that one's value for each field, reading a field of a parameter also lists the same slot of every earlier such parameter, and `--replay-cex` passes one value for parameters whose identities are equal. A call of a user function is inlined and its result is a merge of the objects the callee returns, so a field write to it reaches each of them under the condition that selects it (a callee that returns its parameter writes the caller's value). The following are **`Skipped`** as `unsupported-opcode`: a field write to a value that is not an allocation, a parameter, a merge of them or a user call's result (an extern call's result, say), and a field of any other type (a float or 128-bit field of a value reached through another field). A pointer written into a field (`S { ids: a }`, `h.items = v`) is stored as the address of the object, which stays a model of its own (see "Memory read through a field" below). The payload of an enum, `Option` or `Result` parameter that is itself an aggregate (a struct, or another enum) is an object of its own, one per parameter and slot, whose fields are symbols like a parameter's (`o.1` holds the payload, so its first field is `o.1.0` in a counterexample, and an object it holds in turn is `o.1.1.0`): two reads of one payload are one object, the payloads of two parameters are two, and nothing is assumed about their fields. A payload read from a parameter (or from the payload of one, through an inlined call as well) is that object while the function writes no parameter. The payload of an enum the function builds, of a merge of parameters, or read beside a write to a parameter (the payload may be that parameter) or in a function whose parameters may be one object, is read like a struct held in a field instead: the slot holds the address of the object, and the object at it is the one the function stored there, the parameter whose address it is, or memory the caller gave (see "Memory read through a field" below). So `Option::Some(Handle { fd: a })` read back is that `Handle` (a write to it after it went into the `Option` is what the payload reads), a payload read from `if c { a } else { b }` is the payload of the parameter the condition picks, and after `h.fd = 5` a payload read is 5 exactly when its address is `h`'s. A counterexample lists the slot as the address it holds (`o.1`, equal to `h.addr` when the payload is `h`) and not the payload's fields, and `--replay-cex` rebuilds it only when the address is a parameter's. The model does not know a payload's type, so a parameter of another type may be it, as for a struct field. A payload that is a `Vec` or a `String` (`Option<Vec<i64>>`, `Result<String, _>`) is read as a handle too, and `len`, `get`, `byte_at` and the other reads of it are reads through that address, so the payload is the parameter, the stored object or the memory the caller gave that holds it, as for a struct field; a `Vec` or `String` a function builds around a parameter (`Option::Some(a)`) holds that parameter, which another parameter of its type may be. A write through a payload (`v.push(1)` of the payload `v`), and a payload read from memory read through a handle are **`Skipped`** as `unsupported-opcode`, never guessed at. `--replay-cex` rebuilds the payload object from the entries under its path (see "Native backend" in the `--replay-cex` section). A struct, `Vec` or `String` held in a field of a parameter, and an element of a `Vec`, are not scalarised: they are read through memory (see the same section). A `linear struct` value is an ordinary aggregate here: linearity is enforced by the type checker, so the verifier reads a linear parameter, a linear result and a linear value built in the function like any struct (`drop` and a consume are no-ops, and a counterexample lists a linear parameter's fields as `h.0`, `h.1`, ...). A linear value passed to or returned from a call, or held in an enum payload, is modelled as any other struct there. A loop that writes a field of a value built outside its body (a parameter, or an allocation made before the loop) is cut like one that writes a `Vec`: each slot the loop writes is unconstrained at the top of the header, so the loop is decided by its `invariant` rather than by unwinding (a field of a value the body itself builds is fresh each iteration and needs nothing). A write the model cannot attribute to a parameter or an allocation (through the element address of a `Vec<i128>`) leaves the loop to unwinding alone. A `Vec<i128>` or `Vec<u128>` element is `Skipped` as `unmodeled-builtin` (see "Collections").
